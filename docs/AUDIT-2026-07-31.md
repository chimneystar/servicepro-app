## 2. Verified findings (personally checked at source)

### 2.1 CRITICAL — Privilege escalation: any member can make themselves owner

**Evidence:**
- `db/schema.sql:481-483` — policy `profiles_self_update`:
  `for update using (id = auth.uid()) with check (id = auth.uid() and organization_id = public.current_org_id())`.
  The `with check` constrains **`id` and `organization_id` only**. It does **not** constrain `role`.
- `db/022_operations_privacy_team_admin.sql:15-41` — the `protect_last_owner` trigger fires
  `before update of role, active, organization_id`, but its first branch returns immediately when
  `old.role <> 'owner'`. A `tech` promoting themselves is therefore **not** blocked.
- No column-level `GRANT UPDATE (...)` on `public.profiles` exists anywhere in `db/*.sql` (grep returns
  nothing), so the table-wide grant Supabase issues to `authenticated` applies.
- `lib/supabase/client.ts` ships the anon key to the browser by design, so any logged-in user can call
  PostgREST directly with their own JWT — the app UI is not the only path to the table.

**Exploit:** an authenticated `tech` sends
`PATCH /rest/v1/profiles?id=eq.<their-own-uuid>` with body `{"role":"owner"}`.
Result: full owner rights over the tenant — team management, settings, finance, payment configuration.

**Why it matters here:** roles are the *only* thing separating a field technician from the business
owner's financial data. This is the difference between a multi-tenant SaaS and a shared spreadsheet.

**Contrast — the same author got this right elsewhere:** `db/018_product_foundation.sql:177-180`
protects `profile_capabilities` with `... and profile_id <> auth.uid()`, explicitly preventing
self-grant. So this is an **inconsistency, not ignorance** — which is evidence the codebase is
fixable rather than fundamentally naive.

**Fix (small):** add `role` and `active` to the self-update `with check` (pin them to their existing
values), or replace the self-update policy with a column-scoped grant plus an owner-only role-change
path. One migration.

### 2.2 STRUCTURAL — every `/api/*` route is public at the edge

`proxy.ts` + `lib/supabase/middleware.ts:38-52`: the public-path allowlist includes
`path.startsWith("/api/")`. Every API route therefore **must** authenticate itself; the edge does
nothing for them. Several are legitimately public (payment links, webhooks, booking), but this makes
per-route auth load-bearing and easy to forget. Enumeration of which routes actually check is
delegated and pending.

### 2.3 POSITIVE — tenant isolation at the database is genuinely done

Verified by static expansion of both literal `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` and the
dynamic `DO $$ ... EXECUTE format(...)` loops (script: scratchpad `rls_audit2.py`):

- **97 / 97 tables have RLS enabled.**
- **97 / 97 tables have at least one policy** (none are silently deny-all-by-accident).
- `db/013_security_hardening.sql` is a real hardening pass: fixed `search_path` on every function,

My first grep said "50 tables without RLS". That was wrong — it missed the dynamic loops. Corrected
before use. The honest read is that **the security floor here is well above typical AI-generated
CRUD**, which makes 2.1 more surprising, not less.

### 2.10 Core-operations defects — verified at source

Delivered by review and then **re-verified personally** at the cited lines:

**CRITICAL — `app/api/sms/incoming/route.ts` is unauthenticated and cross-tenant.**
Confirmed by reading the whole 38-line file. Three compounding defects:
- **No signature validation at all.** The two sibling voice webhooks (`/api/calls/incoming`,
  `/api/calls/status`) *do* call `validateTwilioSignature`. This one does not. Anyone who learns the
  URL can POST a forged inbound text.
- **Line 23 reads every customer in the entire database** — `admin.from("customers").select(...)`
  under the **service-role client, which bypasses RLS entirely** — and matches on the last 10 digits
  in JS. A phone number shared by two tenants attributes the message to whichever row is returned
  first.
- **Line 26 fails into the wrong tenant.** With no match it does
  `organizations.select("id").limit(1)` and files the message under **an arbitrary business**.
- Line 13 swallows a missing service-role key with `catch { return twiml(); }` — a silent 200.

Consequence: forged or misrouted customer messages appear in a real business's inbox, and every
inbound SMS pulls the full customer table into memory.

**HIGH — recurring jobs poison the dispatch board permanently.** `db/019_operations_growth.sql:4`
adds `jobs.end_date` as **nullable with no default**; line 5 backfills existing rows. Manual creation
is fine (`app/(app)/schedule/actions.ts:19` defaults `end_date` to `scheduled_date`), and the warranty
RPC sets it. But **both** recurring generators — the button
(`app/(app)/recurring/actions.ts:59-64`) and the **nightly cron** (`lib/cron-tasks.ts:15-18`) — omit
it, leaving NULL. The dispatch query
(`app/(app)/dispatch/page.tsx:17`) is `scheduled_date <= date AND (end_date >= date OR end_date IS NULL)`,
so every such job reappears on **every future date, forever**, and the cron adds more each night. The
board silently degrades with no user action.

**HIGH — PostgREST filter injection in global search.** `app/(app)/search/page.tsx:20` interpolates
raw user input into `.or(\`name.ilike.%${q}%,phone.ilike...\`)`. A comma in the query terminates the
condition and injects another (e.g. `a,archived.eq.true`), defeating the page's own
`archived=false` / `deleted_at is null` filters and 500-ing on ordinary punctuation. RLS still bounds
it to the caller's org, so this is **filter injection, not tenant escape** — real, but not a breach.

**HIGH — server actions rely on RLS instead of checking roles.** In `app/(app)/jobs/[id]/actions.ts`,
`updateJobAddress:82`, `setJobStage:340`, `setJobTags:352`, `setJobExpenses:363` and the four delete
actions call `requireProfile()` only — never `assertRole`/`assertCapability` — while the UI gates them
behind `canEdit = profile.role !== "tech"`. A technician can invoke them directly on any job assigned
to them. The capability system in `lib/auth.ts` is **defined but never enforced** in this area.
`updateJobStatus:266` and `schedule/actions.ts:79` are worse: live endpoints, no role check, no status
allow-list, and referenced by no component — a tech can drive a job to `done` and skip signature
capture and clock-out entirely.

**MEDIUM cluster — data-integrity and scale:** the offline sync path never closes open time entries
(so finished jobs bill hours forever) and never drops rejected events (permanent "N updates waiting"
badge); `clockIn` has a read-then-write race with no DB uniqueness on open entries; dispatch
reassignment leaves the previous lead's `job_assignments` row behind; `/schedule` and `/messages` load
**every** job / SMS / customer row in the org with no date filter or limit; `/jobs` truncates at 500
rows with no pagination and no indication, so tab counts silently go wrong; `lib/notify.ts` swallows
every SMS failure in bare `catch {}` so nobody learns a customer text failed.

### 2.11 Money-path defects — the ones that bill a real customer wrongly

The payment *engine* is better than the rest of the app. `lib/core/money.mjs` is integer-only end to
end — `divRoundHalfUp`, per-line `qtyMilli * unitPriceMinor / 1000`, proportional discount allocation
against the taxable base, tax at `taxBase * taxRateBps / 10000`, plus a `Number.isSafeInteger`
overflow guard. Totals cannot drift a cent inside it. `lib/payments/crypto.ts` is AES-256-GCM with a
fresh 12-byte IV, stored auth tag, a required 32-byte key and no insecure fallback. Helcim and Stripe
webhook signatures are HMAC-verified with `crypto.timingSafeEqual`, and Helcim enforces a ±5-minute
replay window. The classic "client posts its own amount" bug is **genuinely absent** — amounts are
re-derived server-side from the document.

The damage is at the seams between those good parts.

**CRITICAL — an estimate deposit is never credited to the invoice. Verified personally.**
`db/schema.sql:170` shows `estimate_id` exists on **`estimate_items` only**; the `invoices` table has
no link back to the estimate it came from. `app/(app)/estimates/actions.ts:71-76`
(`convertEstimateToInvoice`) copies `total_minor` verbatim and records no relationship. Deposits are
stored on `payments.estimate_id`, while `openBalance()` (`lib/payments/server.ts:83`) selects
`.eq("invoice_id", ...)` for an invoice. **A customer who pays a 30% deposit is then invoiced for
100% of the job.** This is the single largest overbilling path in the product, it is silent, and the
office has no screen that would reveal it.

**CRITICAL — Stripe deposits are orphaned and re-chargeable.**
`app/api/stripe/webhook/route.ts:48-53` inserts the deposit payment with `invoice_id: null` **and
never sets `estimate_id`**, so `openBalance` matches nothing and still reports the full deposit due.
The same deposit can be paid again by card, ACH or Zelle.

**HIGH — the invoice screen counts money it did not receive. Verified personally.**
`app/(app)/invoices/[id]/page.tsx:36-37` sums `payments.amount_minor` filtered only by `invoice_id` —
**no `normalized_status` filter and no subtraction of `refunded_minor`**. A declined card or an
in-flight three-day ACH shows the invoice at zero balance. Every other reader in the codebase gets
this right (`server.ts:82-87`, `server.ts:326-330`, `settings/payments/actions.ts:164-166` all filter
to `['settled','partially_refunded']` and net out refunds) — so this is one screen out of step, not a
systemic misunderstanding.

**HIGH — reporting overstates both revenue and margin.** `app/(app)/reports/page.tsx:76` computes
"Revenue collected" as the sum of `total_minor` over invoices with `status='paid'` — ignoring partial
payments, refunds, surcharges and deposits — while line 79 computes gross profit from item-level
figures that *exclude* discount and tax. On any discounted invoice the margin KPI exceeds reality.
Duplicated in `reports/custom/page.tsx:43-47`. The owner makes payroll and tax decisions on these.
Commission (`reports/commission/page.tsx:35`) pays technicians on `jobs.price_minor` — quoted, not
collected.

**HIGH — duplicate-payment windows.** Manual Zelle/check submissions have no DB-level uniqueness
covering them (the partial indexes at `db/017_helcim_payments.sql:183-192` apply only to
`card`/`ach`), leaving a check-then-insert race; the Stripe webhook has no timestamp tolerance so a
captured signed body replays forever, and it discards the payment-insert error, so an invoice can be
marked paid with **no payment row**; `convertEstimateToInvoice` has no idempotency guard and will mint
a second invoice with a second document number on a repeat call.

**MEDIUM — float arithmetic on money, in exactly one corner.** `app/(app)/finance/actions.ts:10`
uses `Math.round(Number(value) * 100)` for every settlement, tax-filing and dispute figure; the same
pattern is in `operations/actions.ts:47-49` and `growth/actions.ts:23`. Every *other* money entry
point correctly uses `parseAmountToMinor`. Non-numeric input yields `NaN`, silently stored as null.

**Notable — tenant crossover on money is genuinely blocked.** RLS `payments_rw`, the
`assert_child_org` triggers registered for `payments.invoice_id`/`estimate_id`, and composite
`(id, organization_id)` foreign keys form three independent layers. This one was attacked and held.

**Feature reality in the money area:** refunds, tips, saved payment methods, ACH-hold-until-settled,
payment schedules/milestones, automation rules, campaigns and referral sending, tax-jurisdiction
calculation, and inventory movement ledgers are all **STUB** — settings toggles and tables with no
executor behind them. Purchase orders store a single line and never advance status or touch
inventory.

### 2.12 A second privilege-escalation path — same shape as the first

**CRITICAL, verified personally.** `db/schema.sql:494-501` creates `invitations_rw` in a DO-loop:
`for all using (organization_id = current_org_id() and current_user_role() in ('owner','office'))
with check (…same…)`. The `with check` constrains org and *caller* role — **not the `role` column of
the row being written**. So an **office** user can insert an invitation carrying `role: 'owner'`.

`accept_invitation()` (`db/003_team.sql:29-31`) then does
`insert into public.profiles (…, role) values (auth.uid(), inv.organization_id, '', inv.role)` —
**`inv.role` verbatim, unvalidated**.

Chain: office user POSTs to `/rest/v1/invitations` with `{email: <address they control>, role: "owner"}`,
registers that address, and calls `accept_invitation()`. They are now owner.

The server action does require owner (`app/(app)/team/actions.ts:17,24`) — but **the server action is
not the security boundary**. Supabase exposes PostgREST directly and the anon key is in the browser by
design.

**The pattern is now clear and it is the single most important technical finding in this audit:**
both escalation paths (this and §2.1) are the *same defect class* — a `with check` clause that
constrains the row's tenant and the caller's role, but forgets to constrain the privilege-bearing
column being written. The architecture is right; two specific policies are under-constrained. Both are
one-migration fixes.

### 2.13 CRITICAL — the daily cron fails open, and it deletes customer data

`app/api/cron/daily/route.ts:19-22`, read in full:

```ts
const secret = process.env.CRON_SECRET;
if (secret && request.headers.get("authorization") !== `Bearer ${secret}`) {
  return NextResponse.json({ ok: false, error: "unauthorized" }, { status: 401 });
}
```

**If `CRON_SECRET` is unset or empty, the guard is skipped entirely** and the endpoint is anonymous —
and `/api/*` is public at the proxy (§2.2). An unauthenticated GET then runs, across **every
organisation on the platform**, `runAutomaticDataRetention()`, which hard-`DELETE`s
`technician_locations`, `sms_messages` and `email_messages` and nulls `call_events.recording_url` for
every org with `auto_enforce = true` (`lib/data-retention.ts:25-27`). It also triggers Twilio sends
and payment reconciliation. When the secret *is* set, the comparison is a plain `!==` — not
constant-time.

**Compounding it: the route always reports success.** Lines 23-29 wrap all five subsystems in
`try/catch` that stow the error in a JSON field and return HTTP 200 `{ok: true}`. Reminders,
reconciliation, receipts and retention can all fail every night and Vercel's cron dashboard stays
green — the textbook "armed is not alive" failure.

> Run `schema.sql`, then `002_*` … `015_*`, followed by `017_*`, then create the two storage buckets.

**It stops at 017.** Migrations **018, 019, 020, 021 and 022 — roughly 1,370 lines of DDL** covering

### 2.15 Public-surface and privacy findings

- **HIGH — a signed document can be re-signed forever.** `db/004_sharing.sql:65-83`,
  `approve_document`, is granted to `anon` and unconditionally overwrites `signer_name`, `signed_at`
  and `signature_data` with **no `signed_at is null` guard and no rate limit**. The UI merely hides
  the form. Anyone holding the link can replace an existing signature with any name.
- **HIGH — the customer portal token is permanent and un-revocable.** `db/010_v13.sql:15` makes
  `customers.portal_token` a defaulted `gen_random_uuid()` column with **no expiry and no rotation
  path anywhere in `db/*.sql`**. `db/019_operations_growth.sql:259-262` returns to an anonymous holder
  the customer's contact details, the org profile, every job, and **every estimate and invoice
  including each document's `public_token`** — i.e. signing and payment access to all of them. One
  forwarded link is a permanent breach with no revocation.
- **HIGH — the GDPR export ships secrets to the requester.**
  `app/api/privacy/export/[requestId]/route.ts:13` uses `select("*")`, which includes
  `customers.portal_token`, both `public_token`s, `signature_data` and internal cost/margin columns.
  *Authorization is correct* — owner-only, org-scoped, RLS-bound client; cross-org export is not
  possible.
- **MEDIUM — booking time maths has no timezone.** `lib/booking.ts:32,34,46` construct bare
  `new Date("YYYY-MM-DDT…")` and `booking_settings` has no timezone column. On Vercel (UTC) a business
  in UTC-6 gets wrong minimum-notice cutoffs and wrong day boundaries.
- **MEDIUM — `enforce_service_area` silently does nothing for polygon-only orgs.**
  `lib/booking.ts:58-59` filters polygons out, then returns `true` when nothing is left. Polygons are
  never evaluated anywhere.
- **MEDIUM — invitations are never delivered.** No email is sent for an invitation anywhere in the
  codebase; the generated `token` column is written and never used. The UI tells the owner to notify
  the person out of band.
- **MEDIUM — reminders are marked sent before sending.** `lib/cron-tasks.ts:41-45,57-61` write the
  `reminder_log` idempotency row *before* `sendSms`, inside a swallowing `try/catch`. Any Twilio
  failure permanently suppresses that reminder — it can never be retried.

### 2.16 Correction to one delegated claim — role gaps on finance pages are shallower than reported

It was reported that a technician can reach `/invoices`, `/invoices/[id]`, `/estimates` and
`/estimates/[id]` by URL because those pages call `requireProfile()` with no role check. **The page
half is true.** But `db/schema.sql:533-538` puts `estimates`, `estimate_items`, `invoices`,
`invoice_items` and `expenses` in a `finance_tables` loop whose `_select` policy requires
`current_user_role() in ('owner','office')`. A technician therefore loads an **empty page**, not
financial data.

This is a real defence-in-depth gap and the manifest's role claim is genuinely unenforced in code —
but it is **not** a data exposure, and it should not be counted as one. Verified before repeating.

Separately confirmed while checking this: `jobs_update` (`db/schema.sql:550-554`) has
`with check (organization_id = public.current_org_id())` **only** — so a technician assigned to a job
can update *any* column on it, including `price_minor`. That one is real.

### 2.17 HIGH — onboarding offers a currency the payment system cannot serve

Verified across three files:

- `db/schema.sql:57` — `organizations.currency` allows `check (currency in ('USD','ILS','EUR'))`, and
  `app/onboarding/page.tsx:32,49` lets the owner pick one at signup.
- `db/017_helcim_payments.sql:162` — `payment_requests.currency text not null default 'USD'
  **check (currency = 'USD')**`.
- `lib/payments/server.ts:135` — the Helcim card/ACH path **explicitly and gracefully refuses**:
  `if (document.currency !== "USD") throw new PaymentError("Helcim payments currently require USD",
  "currency_not_supported", 409)`.
- `lib/payments/server.ts:374` — the manual (Zelle / mailed-check) path inserts
  `currency: document.currency` with **no such guard**, so for an ILS or EUR organisation the insert
  **violates the check constraint** and surfaces as a raw Postgres error.

**Net effect:** an organisation that selects ILS or EUR during onboarding has *no working online
payment method at all* — card and ACH refuse by design, and manual submission crashes. The single
largest migration in the repo (`017_helcim_payments.sql`, 34 KB) serves USD customers only.

This is worth flagging beyond its severity because the product is otherwise **deliberately
bilingual** — `lib/i18n.ts` carries 240 symmetric English/Hebrew keys, RTL is handled properly
throughout with logical CSS properties (`insetInlineStart`, `textAlign: "start"`), and the money
engine formats ILS. Someone invested real effort in serving a Hebrew-speaking market, and the
payments layer silently does not. **Which currency this company actually trades in changes the repair
priority substantially** — see §5.

### 2.18 Architecture and maintainability — the codebase is two codebases

Scores from the structural review, each grounded in counts I spot-checked:

| Dimension | Score | Basis |
|---|---|---|
| Architecture | 4/10 | Correct framework idioms and a real authorization seam, but **no data-access layer** — 403 `supabase.from(` call sites, **64 tables queried directly from page components**, no domain model |
| Code craft | 3/10 | Typecheck and lint pass clean; but **78 of 222 source files (35%) contain a line over 300 characters** — one is 5,584 chars. Two i18n systems, two form APIs, three action contracts |
| Data model | 4/10 | Genuinely competent tenancy, consistent `bigint` minor units and `timestamptz`, every FK has an explicit `ON DELETE`, all migrations idempotent, **zero `DROP TABLE`/`DROP COLUMN` in the whole tree** — undermined by 12 overlapping table pairs and missing hot indexes |
| Maintainability | 3/10 | Undiffable files, silent write failures, untyped DB boundary, stale runbook, red test suite |

**The decisive structural fact: the quality is stratified by build wave, not spread evenly.**
Waves ≤016 (the core CRM — jobs, customers, schedule, estimates, invoices) rate about a **6**. Waves
017-022, which added **53 of the 97 tables in roughly two days**, rate about a **2**. Treating this as
one uniform codebase is the analytical error to avoid.

Concrete overlaps that will cost real money to live with:
- **Four parallel line-item tables** — `estimate_items`, `invoice_items`, `job_items` are
  column-for-column identical.
- **Three job-status models** — the `jobs.status` enum, `jobs.stage` text, and a `job_statuses`
  table, with no foreign key between stage and the table.
- **Three permission systems** — `profiles.role`, `profile_payment_permissions`,
  `profile_capabilities` — and they are not wired together: `017` policies use `current_user_role()`
  while `022` uses `current_user_can()`, so **`profile_capabilities.can_manage_payments` has no
  effect on payment settings**.
- **Three assignment models** — `jobs.assigned_to`, `job_assignments`, and `crews`/`crew_members`.
  **Only `assigned_to` is covered by the no-double-book exclusion constraint**
  (`db/schema.sql:132-135`, verified), so crew assignment silently bypasses the product's headline
  scheduling guarantee.

**Verified miscellany:** `htmlFor` appears **zero times in the entire codebase** — no form control in
the app is programmatically labelled; 149 `<button>` tags carry no `type`, so inside a form they
default to submit; Tailwind is installed and configured but effectively unused (~31 utility usages
against 871 inline `style={{}}` objects); `/expenses` and `/search` are **fully built features with
no navigation link anywhere** — reachable only by typing the URL.

**What is genuinely good, and would have to be rebuilt from nothing:** `lib/documents.ts` is a real
domain module serving both estimates and invoices with server-authoritative recomputation ("the
client can never submit a total we didn't calculate"); the shared `lib/core/*.mjs` engines are
imported by 15 application sites *and* 4 test files — actually shared, not copy-pasted; the
client/server split is sound (all 75 `'use client'` files are genuinely interactive leaves, no
browser-side table queries); RTL is done correctly with logical properties.

### 2.20 Adversarial security review — independent verdict

An independent reviewer was asked to **refute** §2.1, §2.2 and §2.3 rather than confirm them, and then
to hunt on its own. Scope covered: 18 API routes, **129 server actions across 35 files**, 97 tables
and ~150 policies, 8 anon-reachable `SECURITY DEFINER` functions, and all 24 `createAdminClient()`
call sites.

**All three claims CONFIRMED.** The RLS arithmetic was re-derived independently by expanding all five
`DO`-loops and lands on 97/97 — matching my own count. Additionally verified clean: **zero
`using (true)` or `with check (true)` policies**, zero permissive `to anon` policies, and no
`FOR ALL`/`INSERT` policy missing a `WITH CHECK`.

**The escalation is worse than I stated.** `profiles.role` is the schema's *single identity oracle* —
`current_org_id()`, `current_user_role()` and `current_user_can()` all read it. After self-promotion,
`current_user_can()` returns `true` unconditionally, unlocking merchant connections, payment settings,
privacy settings, consent records, and every tax/settlement/dispute table. It also **defeats a control
the author deliberately built**: `db/017_helcim_payments.sql:12-13` carries the comment *"existing
self-edit profile policy can never be used to grant oneself financial authority"* — which is precisely
what this permits. The same policy lets a technician set their own `profiles.commission_pct`
(`db/012_v15.sql:73`) — direct payroll manipulation, independent of the role bug.

**Important boundary: escalation is within-tenant only.** Setting `organization_id` to another org
fails the `WITH CHECK`, because `current_org_id()` is `STABLE` and still reads the pre-update row.
**No cross-tenant data leak was found by any path.** That is the finding that most supports repairing
rather than rewriting.

**New findings I verified personally:**

- **HIGH — arbitrary storage deletion (IDOR).** `app/(app)/jobs/[id]/actions.ts:255-258`:
  `deletePhoto(id, path, jobId)` calls `await requireProfile()` — no role check — then
  `storage.from("job-photos").remove([path])` with a **fully client-supplied `path`**, never verified
  against the `job_photos` row for `id`. The storage delete also happens *before* the row delete and
  its error is unchecked, so the file is gone even when the row delete fails.
- **HIGH — branded phishing from the business's own identity.**
  `app/(app)/share-actions.ts:14-33`: `autoSendDocument(token, channel, to, origin)` takes **both the
  recipient and the `origin`** from the client and builds `const link = \`${origin}/p/${token}\``,
  which is interpolated into `<a href="${link}">` and sent via the org's Resend/Twilio identity. Any
  authenticated user — including a technician — can email `https://evil.com/p/<token>` to any address,
  branded as the business. `doc.customer?.name` is also interpolated into HTML unescaped, and there is
  no check that the document's org matches the caller's.
- **MEDIUM — `item-photos` bucket has no storage policies at all.** `db/002_batch1.sql:24-38` defines
  org-prefix policies for `job-photos` only, while `DocEditor.tsx:35` and `DocForm.tsx:38` upload to
  `item-photos`, documented as public. Every uploaded item image is world-readable by URL.
- **MEDIUM — payout instructions exposed to any link holder.** `db/017_helcim_payments.sql:533-547`:
  `public_payment_options` returns `zelle_recipient_name/email/phone/qr_url` and
  `check_payee/address`. Chained with the portal-token issue (§2.15), one forwarded link harvests the
  business's entire payment-collection identity.
- **MEDIUM — techs can rewrite colleagues' timesheets and see all cost data.**
  `db/009_v11.sql:97-100` leaves `job_time_entries.user_id` unconstrained; `db/019:217-218` applies a
  blanket org-only `select` across 24 tables with **no role predicate**, exposing vendor costs,
  subcontractor rates, marketing spend and **every colleague's full GPS history**. (`db/021:164` does
  add the role check — so again, an inconsistency rather than a misunderstanding.)
- **MEDIUM — `anon` retains default table grants on 32 pre-017 tables**, including `customers`,
  `jobs`, `invoices`, `payments` and `audit_log`. Later migrations all `revoke all ... from anon`;
  the older ones never did. It is currently fail-closed **only** because `013:53-56` revokes `execute`
  on the helper functions from `anon` — a single point of failure protecting the oldest tables.
- **MEDIUM — tenant-writable billing.** `subscriptions_rw` lets an owner set `status='active'` with an
  arbitrary period end, bypassing SaaS billing; fabricated `settled` rows in `payments` silently zero
  the balance shown to customers.
- **Confirmed the cron fail-open is the DEFAULT, not an edge case:** `.env.example:38` ships
  `CRON_SECRET=` blank.

**Verified clean — no findings (checked, not assumed):** no secrets in the tree; all six
`NEXT_PUBLIC_` vars are legitimately public and no server secret crosses into a client component
(`lib/voice-provider.ts:1` uses `import "server-only"`); **zero** `dangerouslySetInnerHTML`,
`innerHTML`, `eval` or `new Function`; no open redirect; no SSRF (all outbound `fetch` targets are
constants); no SQL injection (the only runtime dynamic SQL uses `%I` on definition-time literals and
binds row data); **no JWT-claim spoofing** — the classic Supabase footgun is absent because no helper
reads `auth.jwt()`; all tokens are `gen_random_uuid()`, never `Math.random()`.

**And the strongest single data point in favour of repair: of 129 exported server actions, 128
authenticate.** The one exception is intentionally anonymous and token-scoped. `organization_id` is
consistently derived from the session, never from client input.

**The reviewer's summary pattern is exactly right and worth quoting:** this codebase's defences are
*consistently strong at the application layer and consistently weaker at the PostgREST layer*. Every
finding above is exploitable precisely because an attacker can **skip the server actions and talk to
`/rest/v1/` directly with the anon key**. That is the threat model the remaining policy work must be
audited against.

## 3. THE DECISION — repair in place, do not rewrite

### 3.1 The verdict

**Fix it. Do not rewrite.** But do not ship it either — this build must not touch a real customer
until the blockers in §4 are closed.

The rewrite question is not "is this code good?" Much of it is not. The question is whether the
**expensive** asset is sound, because that is the only part a rewrite would have to re-derive from
nothing. The measurements say it is:

- **The tenancy model is real work and it holds.** 97/97 tables with RLS and policies, composite
  `(id, organization_id)` foreign keys, `assert_child_org` triggers, a deliberate hardening migration
  (fixed `search_path` on every function, `EXECUTE` revoked from `PUBLIC`, exactly five intentional
  anonymous entry points), and `016_isolation_tests.sql` as executable proof. The money path was
  attacked specifically for cross-tenant writes and **held on three independent layers**.
- **The money engine is correct.** Integer minor units end to end, half-up rounding, proportional
  discount allocation against the taxable base, an overflow guard, and real unit tests. Totals cannot
  drift a cent inside it. Server-authoritative recomputation means the client can never submit its own
  total. Most greenfield attempts get this wrong on the first pass.
- **The credential and webhook handling is correct.** AES-256-GCM with a fresh IV and stored auth tag,
  HMAC signature verification with `crypto.timingSafeEqual`, a ±5-minute replay window on Helcim.
- **The bilingual product is weeks of native-speaker work** — 240 symmetric Hebrew/English keys plus
  RTL done properly with logical CSS properties. No rewrite plan ever budgets for this, and machine
  translation will not reproduce it at product quality.
- **It compiles, lints and builds clean**, on six runtime dependencies.

What is bad is the cheap half: formatting, error plumbing, missing types, missing indexes, duplicated
scaffolding, absent tests. Those are mechanical to fix — and a rewrite would have to build every one
of them anyway.

**The arithmetic settles it: repair is ~26 engineer-weeks (~11 for a triage subset that is safely
operable); a rewrite is 45-60, and 70+ without the existing schema and screens as a specification.
Paying roughly double to discard the working half is not a defensible trade.**

Two further facts weigh in favour. First, the codebase already **demonstrates it knows how to factor
well** — `lib/documents.ts` serving both estimates and invoices, the shared `lib/core/*.mjs` engines
imported by 15 application sites and 4 test files. Propagating patterns that already exist in-tree is
a far shorter path than inventing them. Second, and most tellingly, **the two critical
privilege-escalation holes are the same one-line defect class** (a `with check` that constrains the
tenant and the caller's role but forgets the privilege-bearing column) while the *neighbouring*
policy on `profile_capabilities` gets it exactly right, with `profile_id <> auth.uid()`. That is not
a codebase that misunderstands security. It is one that was built too fast to be consistent.

### 3.2 The honest argument against this recommendation

**The bad code is not evenly spread — it is a distinct, recent, separable 40%, and the strongest
version of "rewrite" is really "amputate."**

Waves 017-022 added 53 of 97 tables in about two days. That layer holds the redundant assignment
models, the third permission system, the settings sprawl, the actions with no error contract, and the
float money maths. And the feature inventory shows **it is largely not real**: of 19 outright stubs,
almost all live there — refunds, tips, saved payment methods, payment schedules, automation rules,
campaigns, referral programmes, custom fields, feature flags, inventory movements, push delivery.
`/fleet`, `/growth`, `/migration`, `/operations` and `/admin` each have a single navigation link and
have never been used by a real business.

**If the company's actual need is the core CRM, deleting waves 019-022 and remediating only the core
is roughly 12 weeks instead of 26 — and lands a better product than fixing 97 tables.** That is a
scope decision, and it is the owner's to make, not mine. It does not change the verdict (still repair,
not rewrite) — it changes how much gets repaired. I have put the question in §5.

### 3.3 What this codebase actually is

It is not amateur work and it is not production software. It is **one week of very fast, very broad
generation with a genuinely strong database foundation and a thin, uneven application layer on top**,
where roughly a third of the surface is scaffolding for features that were never finished. The
previous author knew multi-tenancy, integer money, authenticated encryption and RLS — and never once
ran the test suite they wrote (§2.7). That combination explains everything in this report.
